Agent runtime · multi-tenant · built and audited

theSide.io Intelligence Platform

Each night the platform reads a client's live data (ads, calendar, CRM, search, reviews) and proposes actions. A critic removes the weak ones. A deterministic ranker orders what survives, and an operator approves. Approved actions run through one of nine connectors. The result is measured 7, 14 and 28 days later, and what was learned is written back as memory the next run reads.

9connectors (ads, CRM, calendar, search, reviews, practice management)
32tables, including quarantine, history and idempotency-claim tables
7/14/28day outcome attribution on every approved action
Proposer (forced structured output) Critic Ranker (deterministic) Supervisor → human approves Execute with an idempotency claim, signed audit row

My role: I defined the product, the agent roles, the data model, the approval and service-tier model, and the acceptance criteria. I directed the build, reviewed the diffs and tested the flows. I did not hand-write most of the code. Status, September 2026: the runtime, schema, connectors, approval and audit paths are implemented and tested (0 TypeScript errors, 0 ESLint findings across 369 files, 21 test groups; 63 more regression tests added in this month's audit). The nightly loop proposed recommendations for a first tenant in May 2026. It has not executed actions in production, and it is idle until the worker runtime it was pinned to is replaced. The blocker register and the target architecture for that are written, and the Atlas links them.

Autonomous engine · runs nightly · ships its own code

Nightshift and the Side Studios engine

A 19-node LangGraph state graph runs at 08:23 UTC. It crawls theside.studio and runs nine analyzer categories. It sweeps 20 positioning queries against a ChatGPT-class answer engine to record who gets cited, then scores two separate grades. It drafts one page through writer, designer, illustrator and brand-QA nodes, with a bounded revision loop. A decision layer then picks up to three missions, dispatches AI coding agents in their own worktrees, verifies them, and lands them by trust class. I can revert anything. There is no approval control anywhere in the console, on purpose.

My role: I wrote the spec and the trust ladder, set the budgets and the gates, directed the build, and read it every morning. A revenue system, through three technology generations

The product I am known for, and the reason I care about gates. Built for pre-construction real-estate agents in 2020-21, before generative AI.

Revenue system · pre-construction real estate

From first touch to transaction

Project-marketing firms served developers. Nothing served the agent. I designed the acquisition-to-close system that filled that gap: acquire, capture, prequalify, nurture, route, close, with the CRM orchestrating every step. The conversation layer was a rule-based workflow first, and it grew from 50 branches to more than 120. In-house NLU models replaced it, trained on transcripts from 8,000 captured buyer conversations and built by our engineering team. A UBC Master of Data Science capstone team built the lead-warmth classifiers, which we did not ship. LLM agents carry it now.

1,000+buyer conversations handled a day
1% → 3%lead-to-transaction conversion
~$45Myear-one transaction value (transactions closed, not revenue)
Rule-based conversation workflows In-house NLU on proprietary data LLM agents

My role: I found the gap and defined the business model and the customer journey. I designed the funnel and the CRM logic, directed the team through each transition, and productized the service into a subscription agents could buy. I did not build the models. I owned what they had to do.

How I work

Outcome first. I own the system and the result; AI coding agents are how the implementation gets done.

DEFINE

Architecture and acceptance criteria

Operating model, workflows, agent roles, data flows, integration behaviour, and what "correct" means before anything is built.

DIRECT

Agent-directed delivery

I direct Claude Code and Codex through implementation and testing, in worktrees, against the criteria I set. I read the diffs and run the tests.

GATE

Gates by class of change

Human approval where money moves, trust classes where it does not. Scope allowlists, brand checks, and budgets in files the agents cannot edit.

MEASURE

Outcome attribution

Every approved action is checked against what happened 7, 14 and 28 days later. Numbers that could not be measured are shown as gaps.
