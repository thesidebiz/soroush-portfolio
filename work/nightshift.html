01

What it is

Two layers. The first is a 19-node LangGraph state graph with a bounded revision loop, written in Python and run by GitHub Actions. Seven of the nodes call a model or a paid API; twelve are deterministic. It is not a strict DAG: brand QA can send a draft back to the writer with the violations attached, at most twice, and then it ships nothing.

The graph crawls the site and runs nine analyzer categories over what it finds. It refreshes Search Console, reads GA4 and sweeps 20 positioning queries against an answer engine. Then it scores two grades. The business grade covers the things a client pays for. The hygiene grade covers the site's own upkeep. They are never averaged into one number. Averaging them is how a site with perfect metadata and no customers gets a good report.

The second layer is a decision loop. It reads the night's snapshots, the open experiments and the council's directives. Then it picks at most three missions, using a weighted score over search demand, gap severity and the mission-type weights the retro tunes. Each mission goes to a coding agent working in its own worktree with a written acceptance list, and a verifier re-runs the gates on the result.

Then the work lands by trust class, or it waits. Class A goes in the same night once every gate that applies to the change is green: link validation, brand QA, pytest, ruff, lint, typecheck, build and the two required CI workflows. A gate that does not apply to a change is recorded as skipped. Class B opens a pull request and waits one night of canary. Class C is staged for me with a diff and a risk note.

There is no approval control anywhere in the console. Landed work carries a Revert affordance, and class C items wait in a queue with their age, the reason they were staged and the receipts behind them.

The engine cannot widen its own scope, raise its own caps or edit its own gates. Those live in a policy file that sits in class C, so a change to any of them stops in front of me. The in-graph agents cannot edit the engine's own source at all. The engineer agents the decision layer dispatches can, and every change they make goes through the same CI the site uses.

02

What the engine is allowed to count

Once a night the engine puts 20 positioning queries to a single answer-engine surface, ChatGPT with web search, queried through DataForSEO. A query counts as a mention if the brand appears in the prose or our domain appears in a cited link. There is no rank recorded. The surface returns prose, and inventing a position would be a lie about what was measured.

Citations are drawn as a count against the queries asked. The query pack has changed size before, and a percentage would have hidden that. The two grades are kept apart for the same reason: one combined number would hide which of them moved.

A kill gate in the policy file names a date and a minimum number of non-branded search clicks; if the engine has not earned them by then, it stops. A metric that can only go up is decoration, and an engine that grades itself on a metric it chose is worth nothing to a client.

The same rule runs through the measurement code. If the answer-engine credentials are missing in CI, the run emits a loud line saying the measurement was unavailable. A missing measurement is never written down as a zero. An empty or unparseable answer raises an error. Counting a missing answer as a miss would bias the whole series downward, and nobody would ever see it happen.

Where it stands

It runs nightly on our own site first; client sites are enabled one at a time behind the same gates, because the first time this thing writes to somebody else's repository I want to be watching. The console shows every night's receipts, each figure linked to the file in git it was read from, and a number nobody measured is drawn as a gap. Confirming a veto writes one line to a decisions file, and the engine opens the revert pull request on its next run. A kill gate in the policy file names a date and a minimum number of non-branded search clicks; if the engine has not earned them by then, it stops.

05

My role

I defined the specification: two audiences with three questions each, four principles, and phase-gated acceptance criteria with a byte budget per route. Each principle earned its place from a recorded failure, and the spec names the failure beside the rule. The trust classes, the budgets, the projection schema and the locked metrics contract are mine.

I directed the build. Coding agents implemented the spec under those constraints, in their own worktrees, against the same gates the engine uses at night. I reviewed the diffs, ran the suites and rejected what missed. I own what it must do, what it is allowed to do without asking, and whether it did. The unattended landing evidenced here is class A; class B opens a pull request and waits one night of canary, and I merge those myself.

The design decision that matters most here is removing the human merge gate rather than keeping it. The first version was an article factory behind a human review step, and between 1 August and 3 September it produced 34 nights, zero published pages and 37 open pull requests, while its own kill gate counted the freeze against it. The gate was not protecting anything. It was the reason nothing shipped. So I replaced it with a change taxonomy, a set of deterministic gates that hold, and a veto. The veto design has run for seven nights and landed 23 of 29 missions; the sensor graph underneath it has run since July 11.
